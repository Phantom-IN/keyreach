# keyreach roadmap

> keyreach roadmap. Built in public: each item is a feature branch → PR →
> squash-merge into `main`. Phases and acceptance criteria trace to
> [`implementation_plan.md`](implementation_plan.md) (§ references) and
> [`plan.md`](plan.md). Checkboxes track progress.

**How to use this file:** open a tracking issue for an item before starting it,
branch with the item's branch name, and tick the box in the pull request that
completes it. One roadmap item per pull request where practical. See
[`CONTRIBUTING.md`](CONTRIBUTING.md) for the full workflow.

---

## Phase 0 — Foundations

- [x] **R0.1 — Base OSS structure** *(first commit)* — governance, docs, templates, roadmap, hygiene CI. No source code. *Done when:* repo has all governance/docs files and a clean initial commit on `main`.
- [x] **R0.2 — Project scaffold** `feat/r0.2-project-scaffold` — `pyproject.toml` (Apache-2.0, Python 3.11+, deps per `implementation_plan.md` §1, **no AI/LLM deps**), empty `keyreach/` package, Typer CLI entrypoint with `--help`/`--version` only, `pre-commit` config (ruff/black/mypy), pytest harness. *Done when:* `pipx install -e .` works and `keyreach --help` prints; lint/type/test scaffolding runs green with zero real logic. *Also landed:* the `keyreach` name reserved on PyPI (`0.1.0.dev0` placeholder) and `.github/workflows/publish.yml` — token-free publishing via PyPI Trusted Publishing, pulled forward from R1.6 so the name could be held without storing a long-lived API token.
- [x] **R0.3 — Core data models** `feat/r0.3-core-models` — pydantic `Capability`, `Identity`, `ValidationResult`, `Report` (`implementation_plan.md` §4); generate and check in `report.schema.json`; unit tests. *Done when:* models validate and schema is generated deterministically. *Also landed:* the `Severity` enum with an explicit band ordering, and `keyreach/report/schema.py` with a `--check` mode that R0.9 wires in as the schema-drift job.
- [x] **R0.4 — Provider base + registry** `feat/r0.4-provider-registry` — `Provider` base class and deterministic registry/discovery (`implementation_plan.md` §4); tests with a dummy provider. *Done when:* registry loads providers in stable order. *Also landed:* a closed provider-category set with a public `validate_provider()`, and an empty `ProbeContext` protocol that R0.6 fills in without changing any provider signature.
- [x] **R0.5 — Detection layer** `feat/r0.5-detection` — pattern loader, high-confidence prefix matching + deterministic entropy fallback (`implementation_plan.md` §5); table-driven tests. *Done when:* sample keys map to expected providers/confidence deterministically. **Scope change:** this item originally read "seeded with an **attributed** subset of secrets-patterns-db (CC-BY, update `NOTICE`/`THIRD_PARTY_LICENSES.md`)". Verifying that license from the upstream repository showed it is **CC-BY-SA-4.0** (not CC-BY) and that the database self-declares AGPL TruffleHog content with no per-rule provenance — so **nothing was copied**. Patterns are written from vendor documentation, each citing its source URL; `NOTICE`, `THIRD_PARTY_LICENSES.md`, `CREDITS.md` and `plan.md` §5.2 were corrected to record the finding.
- [x] **R0.6 — Engine + HTTP layer** `feat/r0.6-engine-http` — async, rate-limited, **recordable** (record/replay), **redacting**, **read-only-guarded** client + `ProbeContext` (`implementation_plan.md` §6); tests via cassettes. *Done when:* probes run only through `ProbeContext`; non-idempotent methods default-denied; keys masked in recordings. *Also fixed:* ruff's `TID` rules were never in the `select` list, so the `banned-api` block added in R0.2 had been silently inert — the direct-`httpx` ban now actually fires, which is the edit-time half of the `network_isolation` check due in R0.9.
- [x] **R0.7 — Scoring** `feat/r0.7-scoring` — pure, rule-based severity function + rationale (`implementation_plan.md` §7, `plan.md` §6); tests covering every band boundary. *Done when:* identical capability sets always produce identical band + rationale. *Scope change:* §7 sketched the Critical test as `(admin or write) and (data or cost)` evaluated across the whole capability set, which rates a key Critical when one capability writes to something harmless and a *different* one reads something sensitive. Critical now requires a **single** capability that is both; §7 was corrected and gained §7.1. *Also landed:* `Capability.restricted`, the explicit restriction flag §7 always specified but the model did not carry, and the one-band downgrade rule it drives.
- [x] **R0.8 — Reporting** `feat/r0.8-reporting` — terminal + JSON + Markdown renderers, Jinja2 templates, injected timestamp, golden-file + double-run determinism tests (`implementation_plan.md` §9). *Done when:* same inputs reproduce byte-identical reports (modulo timestamp). *Also landed:* `keyreach/report/build.py` (the `EngineResult` → `Report` assembly the plan implied but never named), `Report.notes` so R0.6's collected probe errors reach the reader, a three-valued status (`valid` / `not valid` / **`not probed`**) so an unidentified secret is not reported as rejected, and the removal of `respx` and `syrupy` — declared in R0.2, never used. The CLI is deliberately untouched; `--report`/`--json` belong to **R1.5**.
- [x] **R0.9 — CI guardrails** `feat/r0.9-ci-guardrails` — GitHub Actions: `ai_ban`, `network_isolation`, `read_only`, schema-drift checks, pytest+coverage, ruff/black/mypy (`implementation_plan.md` §11). *Done when:* a PR that adds an AI SDK, a direct socket in `providers/`, or a non-idempotent probe fails CI — **verified by planting all three**, in `tests/test_guardrails.py` and by hand. *Scope change:* §11 said to "grep source for known model API hostnames", which would have made **R1.1 and R1.2 impossible** — enumerating what an exposed Gemini or OpenAI key can reach means naming those hosts. `ai_ban` bans *inference endpoints* instead; §11 gained a §11.1 and `plan.md` §1 now states the line in product terms. *Also landed:* a fourth guardrail (`no_secrets`, promoted from R0.8's test), a 100% coverage floor over `keyreach` and `tools`, a golden-report drift check alongside the schema one, a 3.11/3.12/3.13 test matrix, a wheel-install job that exercises the package from outside the source tree, and a single `ci` anchor job so branch protection needs one required check.

**Phase 0 is complete.** The pipeline, the report formats, and the guardrails that enforce the hard rules all exist. What does not exist is a single provider plugin — so keyreach still cannot analyse a real key. That is **R1.1**.

## Phase 1 — Archetype providers & MVP (v0.1)

- [x] **R1.1 — Google `AIza` provider** `feat/r1.1-google-aiza-provider` — enumerate Maps/Places/Geocode/Roads/**Gemini** read-only (blueprint + credit: gmapsapiscanner, license verified **MIT**); four fixtures; inline credit header. *Done when:* a test `AIza` key yields a capability map incl. any Gemini exposure, scored with rationale. **keyreach can now analyse a real key.** *Scope change:* **FCM is deliberately not probed** — the only known probe for a legacy FCM server key is to *send a message*, which is a write that would push a notification to a real device, outside `plan.md` §11; legacy FCM was decommissioned in 2024 regardless. *Also landed:* `plan.md` §11 gains a rule for **billable read probes** (the Maps Platform meters reads, so establishing a Maps capability costs the key's owner a fraction of a cent — accepted narrowly, and always flagged `incurs_cost`), and the rule that keyreach reports Gemini *reachability* without claiming inference, since Google key restrictions can be scoped to individual methods.
- [x] **R1.2 — OpenAI/Anthropic provider** `feat/r1.2-ai-provider` — identity + model list + billing/tier, read-only; fixtures. *Done when:* AI-key identity/scope enumerated deterministically. **Two plugins, not one** — `openai` and `anthropic` are separate files with separate auth schemes and error vocabularies, which is what makes them the honest test of the plugin contract that **R1.4** checks. *Also landed:* each provider's keys are split into **two families with disjoint endpoint sets** (an `sk-admin-` / `sk-ant-admin` key reaches the administration API and no model; every other key is the reverse), so a key costs two to four requests rather than every probe in the table. *Scope change:* "billing/tier" is reachable only with an administration key — both vendors moved spend data behind one — so it is enumerated for that family and is not, and cannot be, part of an ordinary key's capability map. *Also fixed:* `ai_ban` matched **version-qualified** inference paths, so it could not see `f"{API}/chat/completions"` — the form every provider plugin here actually writes. Found by planting it; the paths are now version-independent with a boundary match, and `tests/test_guardrails.py` plants both the miss and a near-miss that must not fire.
**Phase 1 is four providers in at this point.** `google`, `openai`, `anthropic`
and `aws` cover two categories. Neither AI plugin required a single change to
`keyreach/core/`; **AWS required three** — a clock, secret registration for a
composite credential, and the aggressive flag. That is the evidence **R1.4** was
created to collect, and the question it now has to answer is whether those three
belong in the interface or whether the interface was wrong.

- [x] **R1.3 — AWS provider** `feat/r1.3-aws-provider` — `sts get-caller-identity` + read-only permission inference; aggressive enumeration **opt-in and flagged**; fixtures. *Done when:* default run is minimal/read-only (six probes, all about the credential itself); aggressive mode gated behind `ProbeContext.aggressive`, off by default, and every capability it produces says so. Blueprint credit: enumerate-iam, license verified **GPL-3.0** — copyleft, so nothing could be copied and nothing was; SigV4 and every endpoint were written from AWS's own documentation. **Scope change:** AWS is the first credential that is not one string — nothing can be signed without the secret access key — so keyreach accepts a colon-joined `AKIA…:<secret>[:<session token>]`, and a bare access key ID is detected, reported, and explicitly *not* probed. **Also landed:** three `ProbeContext` hooks AWS forced (`now()` for SigV4 timestamps, `protect()` so a composite credential's parts are masked, `aggressive`) — the first `keyreach/core/` change any provider has required, and the finding **R1.4** now has to weigh. *Known limits, both under-reporting:* regional services are probed in `us-east-1` only, and JSON-RPC-only services (DynamoDB, Secrets Manager, KMS) cannot be reached at all because keyreach default-denies `POST`.
- [x] **R1.4 — Interface acceptance checkpoint** `chore/r1.4-interface-review` — verify the Phase-0 acceptance test: adding the third provider touched only its own file + fixture. *Done when:* confirmed, or the interface is refactored until true. **Verdict: the promise held twice and failed once, and the interface was *incomplete* rather than wrong** — the full evidence is `implementation_plan.md` §4.2. All three members R1.3 added are generic, tested against "does a *named, already-planned* provider need this?": `protect()` is required by Twilio's `AccountSid:AuthToken`, which arrived early in **R1.6** and needed it exactly as predicted, `now()` by any signed-request provider, and `aggressive` by `plan.md` §11 from the start. **No refactor of the probe tables** — the four `enumerate` methods differ in exactly the places that carry the reasoning, and the genuine shared abstraction is the declarative probe runner already scheduled as **R2.8**. *Landed instead:* `tests/test_provider_contract.py`, the contract asserted against every registered plugin including that a credited provider actually appears in `CREDITS.md`, and that the public `ProbeContext` surface matches a reviewed list. *Two defects found by measuring rather than reading:* **every provider was fetching its validation endpoint twice** while its own comment claimed "one request, not two" (fixed with a per-run idempotent response cache in `ProbeClient`; one request saved per provider, and `requests_made` now makes §11's claim measurable), and **`httpx.URL(url, params=None)` silently clears an existing query string**, which no shipped provider hits but the next one would have.
- [x] **R1.5 — CLI UX** `feat/r1.5-cli-ux` — batch input (`-f` / stdin), `--provider`, `--no-enumerate`, `--delay`, `--unmask`, `--fail-on`, fixed exit codes (`implementation_plan.md` §12). **keyreach is usable from a terminal.** *Also landed:* an ASCII startup banner carrying the authorized-use reminder `plan.md` §11 asks for, `--aggressive` and `--quiet`, `-o`, and the rule that **stdout carries only the report** while the banner, warnings and errors go to stderr — so `--json | jq` works. *Scope change:* the console script now points at `keyreach.cli.run` rather than the typer app, because **click exits `2` on a malformed command line and keyreach's `2` means "a finding at or above `--fail-on`"** — the same code for "your CI config has a typo" and "this key is Critical". `run` is a total mapping onto the three documented codes. *Also landed:* `Engine(force_provider=...)` for `--provider`, which records in `Report.notes` that detection was overridden, since a capability map produced that way rests on the operator's claim rather than on a rule.
- [x] **R1.6 — v0.1 release** `chore/r1.6-release-0.1` — reach ≥10 providers across ≥4 categories (cloud, AI, payment, comms); README usage; CHANGELOG; tag `v0.1.0`; PyPI publish workflow *(already landed in R0.2 — this item just uses it)*. *Done when:* `pipx install keyreach` (or test index) works end-to-end. **Shipped: 10 providers across 5 categories** — `stripe` and `razorpay` (payment), `slack`, `twilio` and `telegram` (comms), and `github` (devtools) join the four archetypes. The coverage measure is now **asserted by `tests/test_provider_contract.py`** rather than counted by hand: it was published in three documents from R0.1 onwards and nothing checked it. *Scope change:* **Square and PayPal were dropped and GitHub pulled forward.** Square publishes no access-token prefix, so a detection rule for it could only have been written from a guess, which `detection_rules.yml` forbids; PayPal's only validation path mints an OAuth token, a POST that creates state and needs the argued `read_only_post` review that **R2.1** is the right place for. GitHub took the slot because its documented `X-OAuth-Scopes` header lets keyreach report a **write** without performing one — the first provider that can. *Also landed:* the ai_ban endpoint list turned out to collide with Twilio's real `/Messages.json` resource, separated only by casing, so that case sensitivity is now pinned in both directions by a planted test instead of being an accident of how the check was written.

**Phase 1 is complete, and v0.1.0 is released.** Ten providers across five
categories, a CLI, and the three guarantees — deterministic, read-only, no
AI/LLM — enforced by CI rather than asserted. The interface held: the six
providers R1.6 added touched their own files and their own fixtures, and made no
change to `keyreach/core/` at all. R1.4 predicted that `protect()` would be
needed by a composite credential it had not yet met; Twilio, Razorpay and
Telegram all needed it, and nothing else was needed.

Phase 2 widens coverage and deepens it: more providers, the declarative probe
format (**R2.8**), HTML reports (**R2.9**), and the drift canary (**R2.10**) that
answers the structural risk every one of these plugins carries — a vendor
changing an endpoint without telling anyone.

## Phase 2 — Breadth & depth

- [x] **R2.1 — Payment providers** `feat/r2.1-payment` — **Shipped `paypal` and `paystack`**, taking payment to five providers and keyreach to twelve. *(Stripe and Razorpay landed early in R1.6.)* **Two of the four named here were dropped, both on the same rule, and that is the finding of this item:** `detection_rules.yml` requires every pattern to come from vendor documentation, and **Coinbase** publishes none — its CDP credential is a UUID key id plus a secret requiring ES256 JWT signing, and a rule matching a bare UUID would claim every UUID on the internet. **Flutterwave** documents its *test* secret prefix (`FLWSECK_TEST-`) but not its live one, and matching only test keys would detect the harmless credential while missing the dangerous one; it has also moved to OAuth for v4, which carries the same problem as PayPal below. *Scope change:* **the payment category is migrating from prefixed secret keys to OAuth client credentials, which have no detectable shape at all.** PayPal, Flutterwave v4 and Coinbase CDP are all in that state. That is a structural finding about keyreach's detection layer rather than about any one vendor — recorded in `plan.md` §5.2. *Also landed:* two `keyreach/core/` changes, the first since R1.3 — `Provider.detectable`, so a provider with no publishable credential shape can declare it rather than ship a guessed rule (PayPal is reachable through `--provider`), and `read_only_post` responses joining the per-run cache with the request body in the key, because PayPal needs a token in `validate` and again in `enumerate` and the old rule would have minted two. *Also found:* **Paystack and Stripe document the same `sk_live_`/`sk_test_` prefix** — the first real detection collision, resolved at the probe stage exactly as `implementation_plan.md` §5 specified in R0.5 and nothing had ever exercised.
- [x] **R2.2 — Comms providers** `feat/r2.2-comms` — **Shipped `discord` and `zoom`**, taking comms to five providers and keyreach to fourteen. *(Slack, Twilio and Telegram landed early in R1.6.)* **Discord shipped because R2.1 solved the problem that deferred it:** its bot-token format is still community knowledge rather than published documentation, so it ships `detectable = False` and is reached with `--provider discord` — no guessed rule required. **Zoom generalises R2.1's finding**: it is a three-part Server-to-Server OAuth credential (`account_id:client_id:client_secret`), equally undetectable, which shows that undetectable credentials are a property of the OAuth credential design rather than of the payment category. *Also landed:* **access levels derived from Zoom's documented scope grammar** (`resource:operation:action:role`) rather than from a checked-in list of scope names — a rule instead of a table, because Zoom ships new scopes continuously — and a Discord capability read from the documented `GATEWAY_MESSAGE_CONTENT` application flag, the same shape as Telegram's privacy-mode capability in R1.6. **PubNub is deferred, not refused:** neither its documentation nor its edge API was reachable from this environment, so nothing about its key format or endpoints could be verified from a primary source, and `plan.md` §5.2 does not permit writing a plugin from memory. It needs one session with working access to `pubnub.com/docs`.
- [x] **R2.3 — Email/marketing** `feat/r2.3-email` — **Shipped all five: `sendgrid`, `mailgun`, `postmark`, `resend` and `mailchimp`**, opening the `email` category and taking keyreach to nineteen providers across six categories. The first item since R1.6 to drop nobody. *The finding of this item is a **withdrawal**:* keyreach shipped `^key-[0-9a-f]{32}$` for Mailgun from R0.5, sourced to Mailgun's authentication page. That page now documents only `curl --user 'api:YOUR_API_KEY'` — no prefix, no length, no charset — and neither does any other page Mailgun publishes. A rule whose cited source no longer supports it cannot be re-verified by anybody, which is the one property `detection_rules.yml` promises, so **the rule was withdrawn and `mailgun` ships `detectable = False`**. Every previously undetectable provider (PayPal, Discord, Zoom) never had a published format; **Mailgun is the first where keyreach had one and lost it**, which is drift rather than a vendor's silence — exactly what **R2.10**'s canary is meant to catch without a human re-reading the docs. *Also corrected:* SendGrid's rule pinned `{22}` and `{43}` segment lengths that appear in no SendGrid document; it now matches the shape SendGrid actually publishes in its create-API-key response, at 0.95 rather than a 0.99 the vendor never justified. *Also landed:* **a send capability for every provider that has one, derived and never performed** — SendGrid's from the `mail.send` scope, Resend's from a documented refusal, Mailchimp's from the role, Postmark's from the header its send endpoint requires. keyreach reports that a key can mail a company's audience from its own verified domain without putting a message in anybody's inbox. *Also landed:* **Postmark's token kind is discovered rather than declared** — two token types with different blast radii, identical shapes, and no published format, so both headers are tried and the vendor's refusal names the one it wanted. *Also found:* **Resend documents 403 for an invalid key and answers 400**, and documents **401** for a *live* sending-only key — so the ordinary reading of 401 would retire a working credential. And **`ai_ban` cost this item a probe**: Postmark's outbound-mail search sits under the same lowercase path as an inference endpoint, with nothing in a line of source to separate them, so the probe was dropped and the bounce list carries the recipient-data finding instead. **No `keyreach/core/` change** — five providers, including two undetectable ones and a per-key host derivation, needed nothing added to the interface.
- [x] **R2.4 — Dev/source/CI** `feat/r2.4-devtools` — **Shipped `gitlab`, `bitbucket`, `npm` and `dockerhub`**, taking devtools to five providers and keyreach to twenty-three across six categories. *(GitHub landed early in R1.6.)* **This item began by re-verifying the three devtools rules keyreach already shipped, which is the discipline R2.3 left behind, and all three turned out to be in a different state.** `pypi` held. **`gitlab`'s citation was wrong** — the personal-access-token guide it had pointed at since R0.5 no longer names any prefix, though GitLab does document `glpat-` on its token-prefix table, so the rule survives with a corrected `source`. **`npm`'s rule was withdrawn**, the second withdrawal in two items: npm describes a token only as "a hexadecimal string", which is not a format and contradicts the charset the rule matched, and npm's CLI reference and CI/CD guide both deliberately refuse to print a token value anywhere. *Scope change:* **PyPI ships as a detection rule with no plugin, and that is a new kind of finding.** PyPI documents nine APIs and exactly one takes an API token — `POST upload.pypi.org/legacy/`, which publishes a package. There is no authenticated read at all, so keyreach cannot validate or enumerate a PyPI token without performing a write, and it will not. Undetectable and un-enumerable are different failures and are now recorded separately in `plan.md` §5.2. *Also landed:* **Docker Hub is detectable because its OpenAPI specification examples both prefixes** (`dckr_pat_`, `dckr_oat_`) where its prose token pages publish neither — a machine-readable vendor specification is a primary source, and it is the only place either prefix appears; the prefix also decides which endpoints exist, since Docker documents the accompanying identifier as a username for one kind and an organization name for the other. **GitLab is the third shape keyreach has met for reading a token's own scopes** — a header at GitHub, a resource at SendGrid, a resource carrying `active` and `expires_at` here. *Also found by running the binary:* **Bitbucket's 401 is `content-type: text/plain` with a zero-length body**, not the JSON error envelope its specification documents for other statuses — the first draft of the fixture invented one, which would have passed forever while describing a response Bitbucket does not send. **No `keyreach/core/` change**, for the fourth item running.
- [x] **R2.5 — Databases/data infra** `feat/r2.5-databases` — **Shipped `mongodb`, `supabase`, `redis` and `pinecone`**, opening the `database` category and taking keyreach to twenty-seven providers across seven categories. **Firebase is refused, and the reason is a new kind:** Google documents that "API keys for Firebase services do not need to be treated as secrets, and it's safe to include them in your code or configuration files", and that "none of the Firebase-related APIs use an API key as authorization for calling the API. The API key passed with the API call is only used for identification". A credential that authorises nothing is not a credential, and shipping a provider for it would tell a user their `AIza…` key is a Firebase secret when the vendor says it identifies rather than authorises — while the `google` plugin already probes what an `AIza` key really reaches. The real Firebase exposure is a permissive Security Rule, which is a property of the project rather than of the key and cannot be checked without reading somebody's database. Recorded in `plan.md` §5.2 as a third failure mode alongside undetectable and un-enumerable. *Scope change:* **"Redis" means Redis Cloud's control plane, not a Redis server** — a server credential is a password spoken over RESP on port 6379, which is not HTTP and cannot go through `ProbeContext` at all; the plugin's docstring says so rather than letting the name imply more. *Also landed:* **Supabase is the first provider detectable for its current formats and undetectable for its legacy ones** — `sb_secret_`/`sb_publishable_` have rules, while the legacy `anon` and `service_role` keys are JWTs and a rule matching three base64 segments would claim every JWT ever pasted at keyreach; the plugin instead decodes the token's own `ref` and `role` claims, purely and offline, so a legacy key names its own project host with no request and no guess. **Supabase is also the first `ADMIN` verdict derived from a single vendor sentence about data rather than about API scope**: a secret key is documented as "bypassing Row Level Security", which is the entire access model of a Supabase project. *Also landed:* the **fourth `read_only_post`** (MongoDB Atlas's OAuth exchange), and Pinecone's plain-text rejection body, which has no JSON envelope at all. *Also found by running the binary:* Atlas answers `Invalid credentials provided`, not the `Invalid client credentials` the first draft of the fixture had assumed. *Known gap, recorded rather than half-built:* Atlas's other documented method is **HTTP Digest**, a challenge-response scheme needing two requests per probe and a fixed client nonce to stay deterministic; the rejection note says such a pair is refused here whether or not it is live.
- [x] **R2.6 — Monitoring/observability** `feat/r2.6-monitoring` — **Shipped all four: `datadog`, `sentry`, `newrelic` and `grafana`**, opening the `monitoring` category and taking keyreach to thirty-one providers across eight categories. The second item since R1.6 to drop nobody by name, though each of the four narrows or refuses part of what its vendor issues. **Datadog is the first composite credential where each half is independently meaningful rather than useless alone:** its own docs split "write needs an API key" from "read needs both", so `keyreach 'API_KEY' --provider datadog` validates on its own — unlike every prior composite credential (PayPal, Zoom, MongoDB Atlas), which authenticates nothing until every part is exchanged together. **Sentry's DSN is refused, and it is a new combination rather than a repeat of Firebase's.** A DSN is genuinely write-capable — Sentry documents it submits events — so it is un-enumerable exactly like a New Relic License key or a PyPI token, not "not a credential" like Firebase. But it gets neither a rule nor a plugin, unlike PyPI: Sentry already ships a provider under the same name for auth tokens, and a DSN detection rule would hand a live, working credential to that plugin, which would report it "invalid" for not being one — worse than PyPI's silence. **New Relic ships one key of at least four**, and says why the rest are out: License keys are "a 40-character hexadecimal string" with no prefix — the exact shape of a SHA-1 hash — so no rule could be written without a false-positive rate no other rule in this file carries, and they are separately un-enumerable, since confirming one is live means sending real telemetry. Only the `NRAK-` User key, confirmed from New Relic's REST-API-keys retirement notice, is detected and probed. **Grafana narrows the same way Redis did in R2.5, but for a harder reason.** A self-hosted or self-managed Grafana's service-account tokens (`glsa_`) authenticate against a host Grafana never publishes and the token never names — worse than GitLab's self-managed gap, because GitLab at least has `gitlab.com` as a real default to fall back on. Only Grafana Cloud's organization-level access policy tokens (`glc_`), reachable at a fixed host, are covered. *Also found:* **Sentry has no dedicated "read my own scopes" endpoint** — the same `GET /organizations/` call that proves liveness also carries the `access` array this plugin reads for write/admin detection, an accident of that endpoint's response shape rather than a designed self-identity call. *Also landed:* the **fifth `read_only_post`** (New Relic's NerdGraph query), the first of the five that is not an authentication exchange — NerdGraph is GraphQL, so even a pure read has no GET form at all. *Also found by probing the live API rather than trusting documentation:* Datadog's OpenAPI spec documents only `403` for `/api/v2/validate`; the live API also answers `401`. New Relic's own prose names its REST v2 header `Api-Key`; the live API silently ignores that and reads `X-Api-Key` instead — both confirmed by sending real requests with an invalid key and reading the actual bytes back, the same discipline that found MongoDB Atlas's real rejection message in R2.5. **No `keyreach/core/` change**, for the sixth item running.
- [x] **R2.7 — Generic bearer/JWT inspector** `feat/r2.7-generic-jwt` — **Shipped `generic`**, opening the `generic` category and taking keyreach to thirty-two providers across nine categories. Every provider before this one is built around one issuer's documented format and endpoints; this one exists for the opposite case, and does two things gated on the same credential shape. **Decoding a JWT is finally the home for a pattern this repo has repeatedly kept out of a vendor-specific rule.** R2.2 and R2.5 both excluded "three base64 segments" from Discord's and Supabase's own detection, because a vendor-specific rule matching every JWT ever pasted at keyreach is a false-positive machine. That reasoning never argued JWTs are undetectable — only that no *single vendor* should claim them. `generic` claims no vendor, so it is exactly where that pattern belongs: `detect()` requires the header and payload to actually decode as JSON, not just the shape, and the first detection rule in `detection_rules.yml` sourced to a standard (RFC 7515) rather than a vendor page. **A well-formed, unverified JWT reports `valid=False`, on the same precedent as AWS's bare access key ID.** Decoding needs no network and proves nothing was checked against a server, so `valid=True` would claim more than keyreach did — the same reasoning `keyreach/providers/aws.py` already applies to a bare `AKIA…` with no secret half. The decoded claims still populate `Identity`, because an unverified fact volunteered by the token is more useful than silence. **Timestamps are formatted, not compared:** `exp`/`iat`/`nbf` render as ISO-8601 from the number the token carries, never compared against the current moment, because that comparison would need the clock read `CLAUDE.md` reserves for AWS SigV4 alone. *Scope change:* **"user-directed generic bearer probe" needed a new credential shape, not a new CLI flag.** A bearer token with no known issuer has no endpoint list any provider file could document, so the roadmap's own phrase settled the design: `TOKEN@URL`, colon-composite credentials' sibling — `@` rather than `:` because a URL's own colon after its scheme would make first- or last-colon splitting ambiguous. Only `GET` is ever sent, which the read-only guard would enforce even without `ai_ban`'s static check, since every real inference endpoint this could be pointed at requires `POST`. **No `keyreach/core/` change**, for the seventh item running.
- [x] **R2.8 — Declarative YAML probes** `feat/r2.8-yaml-probes` — **Shipped `keyreach/core/probes.py`, the probe runner `implementation_plan.md` §8 specified, and migrated `npm` and `pinecone` from hand-written `enumerate` methods to `.yml` spec files.** Provider count is unchanged at thirty-two across nine categories — this item restructures two existing plugins rather than adding new ones, on purpose: the point was proving the abstraction, not growing coverage. **This is the first `keyreach/core/` change since R1.3, and it is the one R1.4 predicted rather than one a provider forced.** R1.4's verdict was that the four `enumerate` methods it compared differ in exactly the places that carry the reasoning, and named "the declarative probe runner" as the genuine shared abstraction rather than a base-class refactor of what existed then. Seven items since (R2.1-R2.7) confirmed the prediction by needing nothing from `keyreach/core/` at all; this item cashes it in. **`ProviderRegistry` now discovers two file shapes in one package and cannot tell downstream which one a provider came from** — `.py` modules and `.yml` specs sort together into one `name`-ordered list, and every consumer (the engine, the CLI, `tests/test_provider_contract.py`) sees a `Provider` either way. **The line the format draws is the same line `implementation_plan.md` §8 drew, checked against real plugins rather than assumed:** no identity extraction (Telegram's `getMe` parsing, Supabase's JWT decode), no multi-step auth exchange (PayPal's client-credentials grant, New Relic's GraphQL-only read), and no per-response branching beyond a fixed four-way liveness state machine — 2xx is live, a configured "not accepted" status set is dead, a configured "refused but live" set means the endpoint said no while the key still works, a configured rate-limit set means try again. Reading npm's and Pinecone's hand-written plugins side by side is what showed that state machine was already the same shape with only status codes and note text differing per vendor, which is what makes it data rather than logic. **npm and Pinecone were chosen as the first migration because both already have the shape the format assumes:** single-header auth, no identity, and a liveness check that reuses one of the capability probes rather than spending a second request — the discipline R1.4 made mandatory by caching identical requests. **The contract suite had to learn two ways to introspect a plugin's own reasoning.** `tests/test_provider_contract.py` used to read `inspect.getmodule(type(provider)).__doc__` for a Python plugin's argument and `inspect.getfile` for its source text; a `YamlProvider` has neither a distinct module nor a distinct class, so both now branch through one `_provenance()` helper that reads a YAML provider's `description` field and `source_path` instead — same tests, same guarantees, two shapes underneath. *Also landed:* the same `.yml`/underscore-prefix convention `.py` modules already had (`tests/dummy_providers/_ignored.yml` proves it), and a dedicated `ProbeSpecError` that names which spec file is broken rather than surfacing a bare `pydantic.ValidationError` at registry load.
- [x] **R2.9 — HTML reports** `feat/r2.9-html-report` — **Shipped `keyreach/report/templates/report.html.j2` and `render_html()`**, the fourth output format alongside terminal, JSON and Markdown. One self-contained document — every style rule inlined in a `<style>` block, no external stylesheet, font, script or image — carrying the same ten required contents `plan.md` §7 specifies and the same section order `report.md.j2` already uses, so the two templates read as the same report in two mediums. **The autoescaping loader R0.8 configured to expect this template matches on a literal `.html.j2` filename suffix**, which is why the file is named `report.html.j2` rather than `report_html.j2` or anything else that merely *contains* "html" — a name `select_autoescape`'s `enabled_extensions` would not have matched, silently rendering every capability's vendor-sourced evidence as unescaped markup. `test_html_escapes_a_capability_that_looks_like_markup` proves autoescaping is actually on rather than assuming the R0.8 configuration still applies. **`--report html` refuses `--file`/stdin outright**, rather than concatenating several `<html>` documents into one invalid file or inventing an unspecified batch-index layout neither `plan.md` §7 nor this item's own scope ("a disclosure-ready HTML **template**", singular) describes — JSON and Markdown can batch by concatenation because both remain a single walkable document either way, and HTML structurally cannot. Every golden-snapshot and determinism test already parametrised over `ReportFormat` (`tests/test_determinism.py`, half of `tests/test_render.py`) extended to HTML with no changes beyond adding the enum member and a `SUFFIXES` entry — the same foresight that made `select_autoescape` already HTML-aware in R0.8 paid off a second time. **No `keyreach/core/` change** — this is a `keyreach/report/` item, and the `Report` model `render_html()` reads from was already complete.
- [x] **R2.10 — Drift-canary CI** `feat/r2.10-drift-canary` — **Shipped `tools/drift_canary/` and `.github/workflows/drift-canary.yml`**, the scheduled check `implementation_plan.md` §13.3 specified in advance from R2.3's and R2.4's evidence: re-verify that a rule's cited `source` still documents its format, and that a declarative provider's probes still exist rather than answering `404` or carrying an RFC 8594 deprecation signal. Provider count is unchanged at thirty-two — this item builds the checker, not new coverage. **"Still documents the format" cannot mean re-running a rule's regex against a vendor's prose, so it means a narrower thing: does the format's fixed prefix still appear on the page.** `leading_literals()` reads that prefix out of a pattern's *leading structure* — a literal run, one mandatory alternation group with an optional suffix (recovering Stripe's, Paystack's, Razorpay's and Docker Hub's real prefixes rather than just the characters before the first metacharacter), and an optional group skipped over entirely — and a negative lookahead (OpenAI's `(?!admin-|ant-|proj-|svcacct-)`, naming *other* rules' prefixes) is recognised and excluded rather than misread as this rule's own alternatives. What it cannot read — a leading character class, a format sourced to a standard rather than a vendor (`generic-jwt`, RFC 7515) — it says so by returning no literal rather than guessing one; `tests/test_drift_canary.py` pins the exact result for every currently active rule. **Scope change from `implementation_plan.md` §10's original sketch:** rather than *maintainer-owned* canary credentials probed per provider — real accounts someone has to create, fund and keep alive forever, one per vendor — the endpoint check sends a placeholder credential no real key ever equals and reads the response against the provider's own declared liveness vocabulary; a `404` there means the endpoint is gone exactly as it would with a real key, with none of the operational burden of one. **Endpoint coverage is scoped to declarative (`.yml`) providers, on purpose:** a `.yml` spec already states its probe URLs, their vendor `source` and its liveness vocabulary as data; a hand-written `.py` plugin states the same facts as Python inside `enumerate()`, recoverable only by running the plugin against a real key, which this canary deliberately never has. npm and Pinecone are covered today; every other provider is still covered by the source check, which does not depend on which format a provider is written in, and future `.yml` migrations gain endpoint coverage for free. **Deprecation is read from RFC 8594's `Deprecation`/`Sunset` response headers, not from a vendor's specification** — R2.4 found three Bitbucket endpoints marked deprecated in Atlassian's own OpenAPI document, but no generic tool can diff against every vendor's schema format; the headers are the vendor-agnostic version of the same fact. **The tracking issue is one per drift, not one per run:** the workflow searches for an existing open issue by label before opening a new one, commenting on it instead, so a vendor page that stays broken for three weeks produces one issue with three comments rather than three duplicate issues nobody triages. *Also found:* **ruff's `httpx` ban is repo-wide, not scoped to `providers/`**, unlike the `network_isolation` guardrail — `tools/drift_canary/base.py` needed the same named `per-file-ignores` exemption `keyreach/core/http.py` has, for the opposite reason: that module is where a real key is sent; this one is where no key ever is. **This is not a `keyreach/core/` item and was never going to be one** — `tools/` dev tooling, run by a scheduled workflow rather than by `pytest`, not shipped in the wheel.
